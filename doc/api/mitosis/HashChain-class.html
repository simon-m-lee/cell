HashChain

HashChain class

The rolling hash chain that binds ledger entries.

How it works

Each entry's hash is H(prevHash || seq || pulseDigest || receiptDigest || effectsDigest || deltaDigest || at). The genesis entry's prevHash is the graph id's fingerprint — a Ledger tied to graph G cannot be confused with a Ledger tied to graph H, even if their entries happen to be identical, because the genesis hash differs.

Non-obvious: why a chain, not a Merkle tree

A Merkle tree allows log n membership proofs — an auditor can be convinced that entry k was recorded without reading the whole ledger. That is a real benefit, but it comes at the cost of

  • a tree structure that must be rebuilt on every append (O(n) unless you grow it incrementally, which complicates the store contract);
  • a larger on-disk format (each internal node is a row);
  • a decision about how to handle forked ledgers that is different for a tree than for a chain.

A hash chain gives the linearity guarantee — any tamper breaks the chain from the tampered entry onward, and verify() catches it in a single sequential pass. That is the guarantee the ledger needs. Merkle proofs are a later concern; if they are added, HashChain becomes the leaf hash and a parallel MerkleTree sits alongside it.
