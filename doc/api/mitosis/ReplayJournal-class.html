ReplayJournal

ReplayJournal class

The replay side of the journal.

How it works

Each operation consumes the next recorded effect of the matching kind and asserts that its input digest matches. On mismatch (wrong kind, wrong input, or journal empty), the replay fails loudly with a ReplayDivergenceException — the "reordered effects diverge loudly" mechanism.

Non-obvious: validation happens before consumption

A record is only consumed (cursor advanced) after its kind, label, and input have been validated. A mismatched attempt leaves the record unconsumed, which is what lets assertExhausted (and the engine) report the divergence after a detached mapper continuation has swallowed the thrown exception. Any failed attempt also latches diverged so that a replay which touched a mismatch can never report success, even when all records happen to be consumed afterwards.

Non-obvious: the run and onFire closures are ignored

On the replay side, the caller's run callback is not executed. If it were, the replay would touch the network — which is precisely what replay is supposed to avoid. Instead, the recorded rawOutput is returned. This means that any code path that depends on the run closure's side effects (as opposed to its return value) is not replayed — which is correct: replay reproduces the observations, not the actions.

See also:

  • RecordingJournal — the side that produced the log.
  • ReplayDivergenceException — what a mismatch throws.
