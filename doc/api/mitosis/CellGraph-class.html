CellGraph

CellGraph class

A registered cell graph: the unit of identity and replay in the framework.

When to use

As the container the Ledger and the ReplayEngine operate on. Every graph that is recorded or replayed must first be assembled by CellGraphBuilder.

How it works

A graph's invariants are:

  • Every cell in the graph has a stable id. Registered cells' nuclei are recorded in _CellGraphRegistry; their id getter returns the graph-assigned name.
  • Every cell is reachable from at least one registered root via the bind/Synapses graph, in strict mode. Reachability is computed at build() time and re-validated lazily.
  • No two cells share a name. Enforced by CellGraphBuilder.
  • Every cell's purity is known. The journal refuses to record a cell whose receptor and rule are both Purity.pure without admitting that journaling is a no-op; the engine refuses to replay an effectful cell that was not journalled.

Non-obvious: strict vs. unrestricted

In strict mode (the default), the graph enforces reachability and refuses to bind a cell that is not registered — see _validateBindTarget. CellGraph.unrestricted() disables these checks for tests; it is documented as unsafe and marked @visibleForTesting.

Non-obvious: the graph does not own the cells

The graph is a view, not a container. It holds references to the cells (so they cannot be garbage-collected while the graph is alive), but it does not dispose them, and a cell obtained from outside the graph continues to function after the graph is dropped. That is deliberate — the graph is metadata, not a lifecycle manager. The lifecycle manager is EphemeralPolicy (the journal hooks into it).

See also:

  • CellGraphBuilder — how a graph is assembled.
  • Ledger — the history a graph is bound to.
  • ReplayEngine — the engine that replays into a graph.
