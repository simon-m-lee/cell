# Migrating from Riverpod / BLoC to `cell_flutter`

**Who this guide is for:** a Flutter developer who already has a Riverpod
or BLoC screen and is comparison-shopping state-management options. You
should know Riverpod or BLoC well. You do **not** need to know Cell —
every Cell concept used here is explained as it appears.

**What it is not:** a tutorial, and not a pitch to migrate everything. It
is a migration manual with complete before/after code, annotated diffs,
and an honest answer to the first question every developer asks: *should
I even migrate?*

**Why Cell exists** (the 60-second version): the live
[Audit Trail demo](https://simon-m-lee.github.io/cell/audit-trail/) shows a
state change that is recorded, rejected by a governance gate, and undone
through a recorded compensation — the three mechanisms this guide migrates
you toward.

**Should you migrate at all?** That decision belongs to the
[fair comparison page](../doc/comparison.md) — the six-package matrix
(where Cell loses five rows), the per-package summaries, and the 30-second
decision tree. It tells you *whether*; this guide tells you *how*.

**The reference projects** — three runnable apps, each with passing
tests, are committed next to this guide:

- `example/migration/riverpod_reference/` — the Riverpod "before"
  (`@riverpod` + `build_runner`)
- `example/migration/bloc_reference/` — the BLoC "before" (full `Bloc`
  with events and states)
- `example/migration/cell_reference/` — the Cell "after" (same feature,
  `Cell.txApply` included)

```bash
cd example/migration/<project>
flutter pub get && flutter test
```

---

## 1. The honest answer: should you migrate?

Start here. This table is the guide's credibility anchor — three rows say
**no**.

| You need… | Migrate to Cell? | Why |
|---|---|---|
| A simple counter or a form | **No** | Riverpod is simpler, and its ecosystem is larger. |
| Compile-time provider safety | **No** | Riverpod's codegen is more mature than Cell's zero-codegen model for that specific concern. |
| DevTools and observability | **No** | Riverpod's DevTools is far more developed. |
| **Audit trails for compliance** | **Yes** | Every `Cell.apply` command mints an `ApplyReceipt` (id, timestamp, arguments, vetted flag). Riverpod and BLoC have no equivalent. |
| **Multi-cell atomic commits with rollback** | **Yes** | `Cell.txApply` stages several commands, validates them, and compensates on failure. This is built into the framework. |
| **Restricted views without copying** | **Yes** | `cell.unmodifiable` / `cell.deputy(testRule: …)` share one state with narrowed authority. |
| **Governed state with validation gates** | **Yes** | `TestCell` gates sit in front of every mutation — they cannot be forgotten. |

**If your screen never needs the four "Yes" rows, do not migrate it.**
Cell earns its complexity where the causal trail is a requirement, not a
nicety.

## 2. The Riverpod migration

The reference feature is a todo list with three states (list, filter,
derived filtered list) and an async submission path with validation —
deliberately not a counter.

### 2.1 Before: `riverpod_reference/lib/main.dart`

```dart
// (condensed from example/migration/riverpod_reference/lib/main.dart)
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:riverpod_annotation/riverpod_annotation.dart';

part 'main.g.dart'; // generated by build_runner

@riverpod
class TodoList extends _$TodoList {
  @override
  List<Todo> build() => [];
  void addTodo(String description) { state = [...state, Todo(...)]; }
  void toggleTodo(String id) { state = [...]; }
}

@riverpod
class Filter extends _$Filter {
  @override
  TodoFilter build() => TodoFilter.all;
  void set(TodoFilter filter) => state = filter;
}

@riverpod
List<Todo> filteredTodos(Ref ref) {
  final todos = ref.watch(todoListProvider);
  final filter = ref.watch(filterProvider);
  return switch (filter) { /* … */ };
}

class TodoListScreen extends ConsumerWidget {
  Widget build(BuildContext context, WidgetRef ref) {
    final todos = ref.watch(filteredTodosProvider);
    // UI reads ref.watch; submission goes through
    // ref.read(todoListProvider.notifier).submitTodo(text);
  }
}
```

### 2.2 After: `cell_reference/lib/main.dart`

```dart
// (condensed from example/migration/cell_reference/lib/main.dart)
import 'package:cell_flutter/cell_flutter.dart';

class TodoModel {
  final TodoBook book = TodoBook();                       // audited commands
  final todosCell = Cell.state<List<Todo>>(initial: []);  // reactive list
  final filterCell = Cell.state<TodoFilter>(initial: TodoFilter.all);
  final filteredTodos = Cell.synthesis<Pulse<List<Todo>>>(
    [todosCell.cell, filterCell.cell],
    aggregator: (cells, emit) { /* same switch as before */ },
  );
  final events = Cell.ingress<String>();                  // side effects
  final receipts = <ApplyReceipt>[];

  Future<void> submitTodo(String description) async {
    // validation → events.emit('error: …') or a txApply transaction
    final tx = Cell.txApply();
    await tx.execute(participants: [book], body: (scope) {
      book.apply<Never>(addCommand, tx: scope);   // + compensation
      book.apply<Never>(statsCommand, tx: scope); // + compensation
    });
    todosCell.update(List.of(book.todos));
    events.emit('saved: $description added (+1 stats).');
  }
}

class TodoListScreen extends StatelessWidget {
  // CellBuilder renders cells; CellListener runs side effects;
  // the model arrives by constructor injection (or CellScope).
}
```


### 2.4 Size and dependencies

| Metric | Riverpod reference | Cell reference |
|---|---|---|
| `lib/main.dart` lines | ~190 (+ generated `main.g.dart`) | ~330 |
| State container | `@riverpod` Notifier + generated code | one `TodoModel` + one `TodoBook` |
| Derived state | codegen provider | `Cell.synthesis` (no codegen) |
| Codegen | `build_runner` + `riverpod_generator` required | **none** |
| Runtime deps | `flutter_riverpod` | `cell` + `cell_flutter` |

Riverpod wins on boilerplate for read-only screens. Cell's extra code buys
the receipt ledger and the transaction — decide by the "Should You
Migrate?" table, not by line count.

## 3. The BLoC migration

The reference feature uses a full `Bloc` — `LoadTodos` / `AddTodo` /
`ToggleTodo` events and `TodoLoading` / `TodoLoaded` / `TodoError` states —
because a `Cubit` migration would hide most of the work.

### 3.1 Before: `bloc_reference/lib/main.dart`

```dart
// (condensed from example/migration/bloc_reference/lib/main.dart)
class TodoBloc extends Bloc<TodoEvent, TodoState> {
  TodoBloc() : super(const TodoLoading()) {
    on<LoadTodos>(_onLoad);
    on<AddTodo>(_onAdd);
    on<ToggleTodo>(_onToggle);
  }
  Future<void> _onAdd(AddTodo event, Emitter<TodoState> emit) async { … }
}

class TodoListScreen extends StatelessWidget {
  Widget build(BuildContext context) => BlocListener<TodoBloc, TodoState>(
    listener: (context, state) { if (state is TodoError) { /* snackbar */ } },
    child: BlocBuilder<TodoBloc, TodoState>(
      builder: (context, state) => switch (state) {
        TodoLoading() => const CircularProgressIndicator(),
        TodoLoaded(todos: final todos) => ListView(/* … */),
        TodoError(message: final message) => Text(message),
      },
    ),
  );
}
```

### 3.2 After

The Cell version is the **same `cell_reference` project** as in §2.2 — one
target for both migrations.

### 3.3 The diff, annotated

```diff
- sealed class TodoEvent { … }            // LoadTodos, AddTodo, ToggleTodo
- sealed class TodoState { … }            // Loading, Loaded, Error
- class TodoBloc extends Bloc<TodoEvent, TodoState> { … }
+ // Why: events become ApplyCommands and states become cells. There is no
+ // separate "loading" state class — the list cell starts empty and the
+ // projection updates when the data lands.

- BlocProvider(create: (_) => TodoBloc()..add(const LoadTodos()), …)
+ // Why: provider → constructor injection, or a CellScope in a bigger app.
+ // TodoApp owns one TodoModel and hands it down.

- BlocBuilder<TodoBloc, TodoState>(
-   builder: (context, state) => switch (state) { … },
- )
+ CellValueBuilder<List<Todo>>(
+   cell: model.filteredTodos,
+   builder: (_, todos) => ListView(/* … */),
+ )

- BlocListener<TodoBloc, TodoState>(listener: (context, state) { … })
+ CellListener<String>(
+   cell: model.events.cell,
+   onPulse: (context, pulse) { /* snackbar from the event payload */ },
+ )

- on<AddTodo>(_onAdd);  // one event → one handler
+ // Why: the multi-step submission becomes one transaction. "Add the todo
+ // and bump the stats counter" commits atomically, each command carrying
+ // a compensation. A failed command rolls the whole step back:
+ final tx = Cell.txApply();
+ await tx.execute(participants: [book], body: (scope) {
+   book.apply<Never>(addCommand, tx: scope);    // compensation: removeTodo
+   book.apply<Never>(statsCommand, tx: scope);  // compensation: unbumpStats
+ });
```

**The takeaway:** BLoC's event/state machine compiles down to *commands
and cells*. The only part with no translation is the part Cell adds — the
transaction and its audit receipts.

## 4. What you gain and what you lose

| Dimension | Riverpod / BLoC | Cell | Winner |
|---|---|---|---|
| Learning curve | Moderate | Higher (new concepts: cells, pulses, gates) | **Riverpod / BLoC** |
| Ecosystem (codegen, DevTools) | Mature | Early | **Riverpod / BLoC** |
| Community size | Large | Small | **Riverpod / BLoC** |
| **Audit trail** | Manual (build it yourself) | Built-in `ApplyReceipt` ledger | **Cell** |
| **Transactions** | Manual | Built-in `Cell.txApply` with compensation | **Cell** |
| **Restricted views** | `select` only | `unmodifiable` / `deputy` without copying | **Cell** |
| **Governance** | Convention | `TestCell` gates enforced before mutation | **Cell** |

Read that table as a filter, not a scoreboard: if the top three rows matter
more than the bottom four, stay on Riverpod or BLoC — they are excellent
choices.

## 5. Incremental migration strategy

You do not rewrite the app. You migrate one screen at a time, and both
frameworks run side by side.

**Run both in one app** — Riverpod and `cell_flutter` are ordinary
dependencies; nothing conflicts:

```yaml
dependencies:
  flutter_riverpod: ^3.0.0     # existing screens keep working
  cell: ^2.0.0
  cell_flutter: ^1.0.0
```

**`ProviderScope` and `CellScope` coexist.** Wrap the app in both; migrated
screens register their cells in a `CellScope`, unmigrated screens keep
their providers:

```dart
ProviderScope(
  child: CellScope(
    child: MaterialApp(/* … */),
  ),
)
```

**Which screens first** (in this order):

1. Screens that need an **audit trail** — anything compliance-relevant.
2. Screens with **multi-step mutations** — a partial failure today leaves
   them inconsistent; `txApply` compensates.
3. Screens where you hand out **read-only views** — `unmodifiable`/
   `deputy` replace ad-hoc copies.

Migrate the rest only if the bottom four rows of §4 still matter to you.

## 6. The migration checklist

- [ ] Read the "Should You Migrate?" table — if no row says *Yes* for your
      screen, stop here.
- [ ] Identify one screen that needs Cell's differentiators.
- [ ] Replace the Riverpod/BLoC state container with a `Cell.state` (and a
      command cell if you want receipts).
- [ ] Replace `Consumer` / `BlocBuilder` with `CellBuilder` (or
      `CellValueBuilder` for any `Cell`).
- [ ] Replace side effects with `CellListener`.
- [ ] Replace `BlocProvider` / providers with constructor injection or a
      `CellScope`.
- [ ] Convert multi-step mutations to `Cell.txApply` with compensations.
- [ ] Run the reference tests (`example/migration/*/flutter test`) and the
      migrated screen's own tests.
- [ ] Check the ledger: every `Cell.apply` call mints a receipt — read it
      in the [Audit Trail demo](https://simon-m-lee.github.io/cell/audit-trail/).
- [ ] Decide whether to migrate the next screen.

## Cell concepts used in this guide (one line each)

- **`Cell.state`** — a retained value with an update path and reactive
  readers.
- **`CellBuilder` / `CellValueBuilder`** — rebuild a subtree when a cell
  changes.
- **`CellListener`** — run side effects on pulses without rebuilding.
- **`Cell.synthesis`** — project several cells into one derived value.
- **`Cell.apply`** — submit a *command*; the framework vets it and returns
  an `ApplyReceipt` (accepted, rejected, or staged).
- **`Cell.txApply`** — stage several commands and commit them atomically;
  failures trigger recorded compensations.
- **`TestCell`** — the integrity gate every mutation must pass.
- **`CellScope` / `Cell.ingress`** — app-level dependency injection and the
  side-effect channel.

The full source of the three references is the best documentation:
`example/migration/riverpod_reference/`, `example/migration/bloc_reference/`,
`example/migration/cell_reference/`.
