CellAsyncBuilder

CellAsyncBuilder<V> class

A widget that renders the asynchronous state of any Cell as an AsyncSnapshot<V>.

CellAsyncBuilder is the binding's Async State Renderer — the widget counterpart of StreamBuilder / FutureBuilder, but driven by a cell. It accepts any Cell, not just ValueCell, and gives the builder a full AsyncSnapshot so the widget can distinguish "no data yet" from "data" from "error" cleanly.

Why it is used

  • Async source display: Cell.fromFuture, Cell.fromStream, and Cell.asyncMap return plain Cell; the standard CellBuilder cannot take them. This widget can.
  • AsyncSnapshot ergonomics: the builder receives the same shape it would from StreamBuilder, so switch-patterns on hasData / hasError / connection state transfer directly.
  • Error surfacing: failures of Cell.fromFuture become hasError snapshots. See Error pulses below — fromStream and asyncMap failures are not visible through this widget.

How it works

  1. Seed: on initState, the widget seeds _snapshot from initialSnapshot if provided; otherwise from snapshotForCell, which serves every state-like operator's retained pulse (via Cell.latestPulse) as well as ValueCell; otherwise from AsyncSnapshot<V>.nothing(). See Seed semantics below.
  2. Observe: it opens one Cell.observe<Pulse<Object?>> link on cell and forwards each pulse to _onPulse.
  3. Decode: _onPulse converts the pulse via snapshotForPulse and assigns it to _snapshot. Data pulses produce data snapshots; error pulses produce error snapshots; type-mismatched payloads produce error snapshots.
  4. Build-phase deferral: pulses arriving during persistentCallbacks or midFrameMicrotasks are queued and flushed in one post-frame callback; only the most recent pending pulse is applied. Pulses outside a build phase commit synchronously.
  5. Cell swap: if cell identity changes in didUpdateWidget, the old egress is stopped, _snapshot is re-seeded, and a fresh egress is bound.
  6. Disposal: the egress is stopped and pending pulses cleared.

Snapshot transitions

Before first pulse After a data pulse After an error pulse
ConnectionState.none (AsyncSnapshot.nothing()) active, hasData == true active, hasError == true

ConnectionState.done is never reached. No core operator emits a completion pulse. Cell.fromFuture emits once and stays silent; Cell.fromStream emits until the stream ends and then stays silent; Cell.asyncMap emits per input and never completes. If the widget needs completion detection, compose with a completion cell (see HowTo-CellAsyncBuilder.md).

Design Note: CellAsyncBuilder vs. CellValueBuilder

CellValueBuilder<V> CellAsyncBuilder<V>
Builder receives V? AsyncSnapshot<V>
Distinguishes loading / data / error no (only data) yes
Error pulses reported via FlutterError when emitErrors: true rendered as hasError snapshots
Typical source derived / projection cells async cells (fromFuture, fromStream, asyncMap)

Pick CellValueBuilder for synchronous "latest value" rendering of a non-ValueCell source. Pick CellAsyncBuilder when the builder must branch on loading / data / error — that is, when the cell's history matters, not just its current payload.

Error pulses

Only Cell.fromFuture emits Pulse<Object>(type: 'error') on its failure path. Cell.fromStream and Cell.asyncMap do not emit error pulses in the core package today: a stream error is silently cancelled (or ignored), and an asyncMap mapper failure is dropped. Consequently this widget produces hasError == true only for fromFuture failures (and for type-mismatched data payloads, below). A CellAsyncBuilder over an asyncMap that throws will keep the last successful snapshot — the failure never reaches this widget. Callers who need error visibility from fromStream / asyncMap must bridge those sources through a custom cell that re-emits the failure as an 'error' pulse.

A type-mismatched data payload (a data pulse whose payload is not assignable to V) is also surfaced as hasError — it is a caller bug, not a transient source error. The per-source error-pulse behavior is asserted in test/error_pulse_sources_test.dart.

Seed semantics (please read)

The default seed path uses snapshotForCell → retainedPulseOf, which reads the core package's retained pulse via Cell.latestPulse. A plain async cell (fromFuture, fromStream, asyncMap, derive) that already emitted before this widget subscribed therefore seeds that value into the first frame — a completed fromFuture renders data immediately instead of nothing(). A cell that has never emitted falls back to nothing() until the next live pulse. Pass initialSnapshot only to override the seed (cache hydration, or a snapshot the caller already holds). See test/seed_paths_test.dart for the coverage.

Concurrent asyncMap caveat

When the source is Cell.asyncMap with concurrency > 0 (or overlapping latestOnly futures), this widget inherits the framework's caveat: concurrent effect attribution is tracked separately and is not yet verified end-to-end. The widget's own observation behavior is correct; the caveat is about the source's replay fidelity. See the cell core package for status.

Technical Details

  • One egress per element: the widget owns exactly one observation link; disposal stops it.
  • Coalesced flush: build-phase pulses collapse into one post-frame setState; only the last pending pulse is decoded, which is the right semantics for a "latest value" view.
  • Type erasure at observation: the subscription is typed Pulse<Object?> so error and type-mismatch pulses can be received and decoded; the type check happens inside snapshotForPulse.

Example

final user = Cell.fromFuture<User>(api.fetchUser());

CellAsyncBuilder<User>(
  cell: user,
  builder: (ctx, snapshot) => switch (snapshot) {
    AsyncSnapshot(hasData: true) => ProfileView(snapshot.data!),
    // Only failures of a `fromFuture` source produce hasError — see
    // *Error pulses* above.
    AsyncSnapshot(hasError: true) => ErrorView(snapshot.error!),
    _ => const LoadingSpinner(),
  },
);
