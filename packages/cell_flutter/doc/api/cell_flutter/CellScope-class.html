CellScope

CellScope class

An InheritedWidget that provides a small set of app-level cells to the subtree below it, addressed by Symbol.

CellScope is the binding's App-Level Cell Registry. It exists for the handful of cells that are genuinely global — auth, theme, featureFlags, currentUser — and should not become a general-purpose service locator. Mitosis's philosophy is that cells flow through the tree explicitly; passing a cell as a constructor argument is the default, and CellScope is the escape hatch for the few identifiers that every layer of the app needs to reach by name.

Why it is used

  • Well-known globals: register the small set of cells whose identity is stable for the lifetime of the app, so distant widgets can find them without threading them through every intermediate widget.
  • Symbol-keyed lookup: keys are Symbols (#auth, #theme), not type parameters. A single app commonly has several Cell values of the same V (multiple Cell<User>, several Cell<int>), and type-keyed lookup cannot tell them apart.
  • Subtree scoping: nested CellScopes allow a feature to expose its own cells without polluting the app-wide registry, while still obeying the nearest-scope rule described under Nested scopes.

How it works

  1. Registration: a CellScope takes a Map<Symbol, Cell> and places it in the widget tree above its child.
  2. Lookup: of, maybeOf, and valueOf perform a dependOnInheritedWidgetOfExactType<CellScope>() call, which both retrieves the nearest enclosing scope and registers the caller as a dependent — so the caller is rebuilt only when updateShouldNotify returns true.
  3. Type widening and narrowing: of / maybeOf accept a value-type parameter V and narrow the returned cell to ValueCell<V> when the registration is a ValueCell. Plain Cell registrations are returned unchanged — the value type only exists on the pulse they emit.

Design Note: Symbol keys, not type keys

Type-keyed lookup (Provider<T>, InheritedWidget subclasses per type) fails in a Mitosis app for the same reason it would fail in a rich domain model: type is not identity. #auth and #profile may both be Cell<User>; #theme and #draftTheme may both be Cell<ThemeData>. Symbol keys make the intent explicit at both the registration and the lookup site and enable the debug shadow warning below.

Lookup semantics

Method Unknown id Type mismatch Requires ValueCell
of throws throws no
maybeOf returns null throws no
valueOf throws throws yes

A type mismatch on a ValueCell registration always throws — it is a caller bug, not an absence. Unknown ids return null through maybeOf only; of and valueOf treat them as bugs.

Nested scopes

If a CellScope is nested inside another, dependOnInheritedWidgetOfExactType<CellScope>() returns the nearest one. Inner registrations therefore shadow outer ones for the same Symbol. This matches InheritedWidget's contract. In debug builds _lookup inspects ancestors and emits a debugPrint warning — once per symbol per session — when a lookup finds a registration that would be shadowed by a nearer scope. The warning is usually a sign that a feature scope has accidentally duplicated an app-wide id.

Rebuild behavior

updateShouldNotify returns true only when the effective map changes: a cell at a key is replaced with a cell that is not == to the previous one, or the key set changes length. Cell overrides == as nucleus-based logical identity, so swapping a cell for an equal handle (such as a deputy of the same cell) does not notify dependents. A parent re-build that constructs an equal-but-distinct map — a common accident when the map literal is inlined in build — also does not trigger descendant rebuilds.

Example

// App root:
final auth  = Cell.state<AuthState?>(initial: null);
final theme = Cell.state<ThemeData>(initial: ThemeData.light());

CellScope(
  cells: {
    #auth:  auth.cell,
    #theme: theme.cell,
  },
  child: const MyApp(),
);

// Deep in the tree:
final authCell = CellScope.valueOf<AuthState?>(context, #auth);
CellBuilder<AuthState?>(
  cell: authCell.unmodifiable,
  builder: (_, state) => ...,
);

Parameters:

  • cells: The Registry. A Map<Symbol, Cell> of app-level cells. Keys are the well-known Symbols; values are the Cells they resolve to. Held by reference — the map is not copied.
  • child: The Scoped Subtree. The widget whose descendants may perform lookups against this registry.
