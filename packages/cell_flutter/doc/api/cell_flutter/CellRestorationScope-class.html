CellRestorationScope

CellRestorationScope class

Provides a RestorationBucket to descendant RestorableCells and registers them automatically with Flutter's restoration protocol.

CellRestorationScope is the binding's Restoration Registry — the widget-layer counterpart of CellScope. Placing it above a subtree:

  1. Claims a child RestorationBucket from the nearest enclosing RestorationScope (or RootRestorationScope) under restorationScopeId.
  2. Exposes CellRestorationScopeState.register / CellRestorationScopeState.unregister through the widget tree, which descendant States call for each RestorableCell they own.
  3. Re-registers every known cell on each restoreState callback, so a bucket arriving after mount (process restart) rewrites the restored values into the cells before the next build.

Registration timing (read this)

Register cells from initState or didChangeDependencies — never from build. Registration writes the restored value into the cell, which emits through the reactive graph; doing that during a build phase can trigger a setState-during-build error in observing widgets. The scope itself performs its registration work before descendant initStates run, so initState registration is always safe.

Injected buckets

Passing bucket wraps the scope in an UnmanagedRestorationScope, which is how tests (and hot-restart tooling) inject a specific bucket — e.g. a RestorationBucket.root built from persisted data. Without it, the bucket is claimed from the enclosing RestorationScope as usual.

Nested scopes

Nested CellRestorationScopes claim independent child buckets and restore independently — the same nearest-scope rule as CellScope.

Example

RootRestorationScope(
  restorationId: 'root',
  child: CellRestorationScope(
    restorationScopeId: 'app',
    child: MyApp(),
  ),
);
