FileLedgerStore

FileLedgerStore class

A LedgerStore backed by a single JSONL file.

One ledger per file. Appending is writeFrom in append mode with a trailing newline. A single writer appends entries sequentially and flushes after each one; a crash between flushes is detected by verify on reopen. There is no entry-size limit — entries carry the materialised pulse body and can legitimately grow with the payload.

Non-obvious: no fsync per append

A truly durable ledger fsyncs each entry. That is a synchronous syscall (~0.1-10 ms depending on the device), and doing it per append would cap the ledger at ~100 entries/sec on an SD card. The performance gate (<5% regression on the pure path) cannot tolerate that. Instead, FileLedgerStore flushes after each append (writes go to the OS buffer) and fsyncs on close. A crash between flushes loses at most one entry, and verify() on reopen will report the gap. This is the same trade-off WAL-mode SQLite makes.

Honesty notes (review fixes)

dart:io exposes no per-append fsync; flush() is the strongest available primitive, so fsyncEachAppend is accepted for API compatibility but currently cannot be stronger than the default flush-then-fsync-on-close behaviour. Likewise, appends to a regular file are not atomically visible to concurrent readers regardless of size — the PIPE_BUF-sized entry cap below is retained as a conservative line-size bound, not an atomicity guarantee.
