How to Use Causal Replay

Causal Replay: the in-depth guide.

Everything in this guide is written against the shipped API in package:cell (commit series through c85a36e0). Code samples are the same shapes used by the framework's own test suite (test/replay/) and the executable demos in example/replay/.

Part I — The mental model

1. What causal replay is

Causal replay is the ability to take a recorded history of everything that ever happened to a Cell graph and re-execute it exactly, in a fresh process, against a freshly built copy of the graph, arriving at the same state — or at a deliberately different state, when you are running a what-if branch.

Three ideas carry the whole design:

  1. Causality over state. The ledger records causes (the pulses that entered the graph) and effects (the state deltas they produced), in causal order. Replay re-injects the causes and checks that the effects re-occur.
  2. Purity is declared, not assumed. Code that depends on the outside world (clocks, random numbers, network, timers) must declare itself. The framework refuses to replay undeclared effects loudly — the alternative is a silently wrong reconstruction.
  3. Identity is stable. Every cell has a registered name that means the same thing in the recording process and the replay process. Without stable identity, a ledger entry cannot address the cell it happened to.

The one-sentence contract

If every effect that is not a function of the pulse goes through an EffectJournal, and every cell is registered, and the receptor implementations are versioned, then replaying a ledger into a fresh graph reproduces the recorded state exactly — and any deviation is reported with the ledger sequence number, the expected value, the actual value, and the reason.

2. What it is not

  • Not bit-exact re-execution of arbitrary user code. User functions run again during replay, but their observations are served from the journal. A receptor that performs I/O without journalling is caught by the journal's exhaustion checks — it is not silently re-run.
  • Not a snapshot restore. You do not restore state == X; you reconstruct how X came to be. This is what makes auditing possible: the auditor can replay and then ask "which pulse made this delta?"
  • Not a database migration tool. Replay across a graph shape change (a rewired receptor, a renamed cell) is a migration, not a replay. The framework refuses; migration is the future a future migration revision.
  • Not cross-process without registration. An unregistered cell's id is a process-local hash and cannot be addressed from a ledger file.

3. The recording loop

                       ┌─────────────────────────────────────────┐
 pulse ──▶ receptor ──▶ test rule ──▶ policy ticks ──▶ state delta │
             │              │              │                 │     │
             │              │              │                 │     │
             └── JournalScope ──┴── LedgerScope ──┴── Ledger.appendInternal
                    (effects)      (deltas + effects)        │
                                                              ▼
                                                    hash-chained entry
                                                    (pulse, receipt, effects,
                                                     deltas, timestamps)

During recording:

  1. A mutation enters the graph inside graph.run(...), which pushes a LedgerScope.
  2. The receptor validates the pulse through its TestCell rule, ticks any hosted EphemeralPolicy, and commits the state through ValueCell.postProcessRule.
  3. Every effect (clock, UUID, I/O, timer, rule verdict, policy tick) is written to the ambient RecordingJournal.
  4. Every delta (before value, after value, cell id) is captured by the LedgerScope.
  5. Ledger.appendInternal hashes the pulse digest, the receipt digest, the effects digest and the delta digest into one chain entry. Each entry's prevHash is the previous entry's hash, so tampering with any byte breaks every entry after it.

4. The replay loop

 ledger entry (seq N) ──▶ _checkVersions ──▶ reconstruct pulse ──▶ dispatch
                              │                                        │
                              │                                        ▼
                              │                              fresh graph's receptor
                              │                                  (pure rules re-run,
                              │                                   effectful rules are
                              │                                   served their recorded
                              │                                   verdicts)
                              │                                        │
                              └──▶ ReplayJournal (peek/commit) ◀────────┘
                                        │
                                        ▼
                              assertExhausted + delta comparison
                                        │
                                        ▼
                              success, or DivergenceReport(seq N)

During replay, per ledger entry:

  1. Version check — the recorded receptor/rule versions must match the target graph's live versions or an entry in the graph's VersionRegistry. Otherwise: loud divergence.
  2. Pulse reconstruction — the input pulse is rebuilt from the entry's arguments (first positional argument becomes the payload) or, failing that, from the delta's after value.
  3. Dispatch — the pulse is re-injected into the target graph with a fresh ReplayJournal in scope. Pure rules re-run. effectful rules consume their recorded VerdictEffect and are not re-called. readOnlyExternal rules re-run with their observations served from the journal.
  4. Exhaustion — the journal must be fully consumed; any unused record, any mismatched kind, label or input is a divergence.
  5. Delta verification — after dispatch, every recorded delta's after value is compared with the target cell's current value.

Part II — The 15-minute path

The complete, annotated minimal program. The seven-item pre-flight checklist follows immediately after the code.

import 'dart:io';

import 'package:cell/cell.dart';
import 'package:cell/replay.dart';

Future<void> main() async {
  final dir = await Directory.systemTemp.createTemp('replay_quickstart');

  // ── 1. Build a graph. Registration gives stable ids. ─────────────
  final counter = Cell.state<int>(initial: 0);
  final graph = (CellGraph.builder(graphId: 'quickstart')
        ..registerState('counter', counter))
      .build();

  // ── 2. Bind a ledger. The store's genesis must match the graph. ──
  final path = '${dir.path}/ledger.jsonl';
  final ledger = await graph.bindLedger(
    store: await FileLedgerStore.open(
      path,
      genesisHash: Ledger.genesisHashOf(graph.id),
    ),
  );

  // ── 3. Mutate inside graph.run. ──────────────────────────────────
  await graph.run(() async {
    counter.update(1);
    counter.update(2);
    counter.update(3);
  });

  // ── 4. Verify the chain. ─────────────────────────────────────────
  await ledger.verify();
  print('Recorded ${await ledger.lastSeq + 1} entries.');
  await ledger.close();

  // ── 5. Replay into a fresh graph. ────────────────────────────────
  // The live registry must be cleared before rebuilding the same
  // names (test/demo context; see Part III §6).
  CellGraphRegistry.forceReset();
  final freshCounter = Cell.state<int>(initial: 0);
  final freshGraph = (CellGraph.builder(graphId: 'quickstart')
        ..registerState('counter', freshCounter))
      .build();

  final reopened = await Ledger.open(
    graph: graph,
    store: await FileLedgerStore.open(
      path,
      genesisHash: Ledger.genesisHashOf(graph.id),
    ),
    genesisHash: Ledger.genesisHashOf(graph.id),
  );
  final result = await ReplayEngine.replay(
    ledger: reopened,
    target: freshGraph,
  );

  print('success=${result.success} '
      'entries=${result.entriesReplayed} '
      'value=${freshCounter.cell.value}');
  assert(result.success);
  assert(freshCounter.cell.value == 3); // Cell.state replaces on update

  await reopened.close();
  await dir.delete(recursive: true);
}

Three details that matter even in this minimal example:

  • Cell.state replaces, it does not accumulate. update(1); update(2); update(3) leaves the value at 3. If you need accumulation, write a custom rule or a custom receptor that does the arithmetic.
  • The genesis hash is derived, not invented. A store whose genesis does not match Ledger.genesisHashOf(graph.id) is rejected at bindLedger/Ledger.open (the fork engine enforcement). The examples in early drafts of the phase docs passed arbitrary strings; that no longer works.
  • ReplayEngine.replay refuses a ledgered target. The target graph must be a fresh graph (no ledger bound); replay reconstructs state, it does not merge histories.

The seven-item pre-flight checklist

If a graph satisfies all seven, it is replayable. If it does not, the framework reports which item failed — loudly, not silently.

# Requirement Enforcement
1 Every cell is registered CellGraphBuilder.build throws on unregistered reachability
2 Ledger bound exactly once, with the derived genesis bindLedger throws on double bind; a wrong store genesis throws at open
3 Mutations inside graph.run Non-run mutations are silently unrecorded; the replay test (item 7) catches them
4 I/O operators journalled The five operators require journal:; omitting it is a compile error
5 Purity declared Default is pure; an I/O rule that declares pure fails the determinism check
6 Versions stamped Versioned receptors fail the the governance version check at a boundary; built-ins stay unversioned by design
7 A replay test passes ReplayEngine.replay against a fresh graph asserts result.success

Each item is enforced at a specific place in the source; see Part VI for the invariant-to-enforcement-site mapping.

Part III — The machinery, in depth

6. Stable identity: registration and Cell.id

Why identity is hard

Two cells that "look the same" are only the same cell if the framework says so. A cell created in process A and its counterpart created in process B are different objects — replay is only meaningful if the ledger can address them by a name that is stable across both processes.

The principal chain

Cell.id is resolved by walking the cell's principal chain: a deputy cell inherits the identity of its principal (the cell it was cloned or delegated from), unless it has been registered under its own name. The walk is not free — in debug VM futures it has been measured at ~0.5 ms per call through dynamic record access — so the hot ledger path resolves the id once at the caller's call site and threads the string through (see LedgerScope.recordPulse's comment in the source).

Registration

final counter = Cell.state<int>(initial: 0);
final graph = (CellGraph.builder(graphId: 'g1')
      ..registerState('counter', counter))
    .build();
  • registerState(name, handle) registers a StateHandle's cell under name; register(name, cell) registers any cell.
  • The builder is strict by default: every reachable cell (roots and everything reachable through bind/Synapses) must be registered, or build() throws. CellGraph.builder(strict: false) exists for tests and for the CLI's placeholder graphs; it is documented as unsafe for production.
  • CellGraphRegistry.forceReset() clears the live identity registry. It is @visibleForTesting — application code should build each graph in its own process, or keep one graph alive. Rebuilding the same names in one process without resetting makes the new cells resolve their ids to the old cells.

What registration buys you

  • The ledger can say "cell counter changed from 1 to 2" and the replay process can find "counter" again.
  • graph['counter'] resolves a RegisteredCell (.cell, .name).
  • CellGraphSnapshot (the serialisation layer) can serialise the registered shape; its currentSchemaVersion is 2 as of the governance layer. fromJson accepts versions <= current, so pre--7 snapshots still parse.

7. Purity: the declaration boundary

Purity has three values:

Value Meaning Replay behaviour
pure Output is a function of input and cell state only Re-run exactly; no journal needed
readOnlyExternal Reads the outside world, never mutates it Re-run; every read served from the journal
effectful Mutates the outside world Not re-called; the recorded decision (VerdictEffect) is served

Two mixins attach behaviour to a custom ReceptorBase or TestCell:

  • Effectful — sets purity to effectful. On the recording side the rule runs once; its decision is journaled. With no journal in scope, NullJournal throws on the first effect — by design (an effectful receptor outside a journal scope is a bug to surface, not hide).
  • EffectfulReadOnly — sets purity to readOnlyExternal. The rule re-runs during replay; its journal.io(...) / journal.clock() calls are consumed from the replay journal in order.

The default for every built-in rule and receptor is pure, and that is the correct answer for most custom code. The test question is: "does my output depend on anything other than the input and the cell's state?"

8. The EffectJournal

The journal is the single interface through which every external observation must flow:

abstract class EffectJournal {
  static EffectJournal get current => JournalScope.current;
  int get consumed;
  DateTime clock();                    // the journal
  String uuid();                       // the journal
  Future<T> io<T>({...});              // the journal
  Future<void> timer({...});           // the journal
  Future<bool> verdict({...});         // the governance layer
  void policyTick({...});              // the governance layer
  void push(); void pop();             // journal-scope bookkeeping
  void assertExhausted();              // replay-side completeness
  List<Map<String, Object?>> toJson(); // canonical effect log
}

The recorded effect kinds (all round-trip through canonical JSON via EffectRecord.fromJson):

Kind Record Carries
clock ClockEffect epochMillis
uuid UuidEffect uuid
io IoEffect label, inputDigest, rawOutput
stream StreamEffect stream bookkeeping
timer TimerEffect scheduled, scheduledAtMillis, firedAtMillis
verdict VerdictEffect verdict (bool), ruleLabel, inputDigest
policyTick PolicyTickEffect policyLabel, cellId, inputDigest

The three implementations

  • RecordingJournal executes and records. Its constructor accepts clockSource, uuidSource, and timerScheduler for deterministic tests. Helpers: consumed, recordsSince(n), lastRecord, toJson.
  • ReplayJournal serves and validates. It is constructed from a list of records (ReplayJournal(entry.effects)).
  • NullJournal.instance is the "no journal in scope" sentinel. It throws a loud StateError on every effectful operation. It is deliberately not a silent no-op.

Peek-then-commit

The replay journal never consumes a record until every field has validated. The cursor advances only in _commit(). A validation failure calls _fail(...), which:

  1. latches diverged and divergenceReason on the journal, then
  2. throws ReplayDivergenceException.

The latch is what makes swallowed exceptions visible: an operator's mapper error contract may swallow the throw, but assertExhausted() at the end of the entry's replay re-throws the latched divergence.

_peek(kind)            → kind mismatch?         → _fail, throw
_validate(fields)      → label/input mismatch?  → _fail, throw
_commit()              → cursor++
assertExhausted()      → diverged?  → rethrow the latched reason
                       → remaining > 0? → "journal not exhausted"
                       → ok

Verdicts and policy ticks

journal.verdict(...) wraps an effectful test rule:

  • Recording: run executes once; the returned bool is recorded with the rule label and the input digest.
  • Replay: run is ignored; the recorded verdict is served after the label and the input digest are validated.

journal.policyTick(...) journals one tick of a cell's hosted EphemeralPolicy:

  • Recording: the record is written; the policy callback still runs.
  • Replay: the record is consumed and validated (policyLabel, cellId, inputDigest — the input is the pulse's payload, because a pulse object itself is not stable across record and replay); the policy callback is not re-invoked. The existing CycleChecker.tickPolicy guard still applies the tick on both sides, which is the the cycle-checker reseed fix: tick order is now part of the recorded history.

9. JournalScope: the ambient journal

JournalScope keeps a Zone-local stack of journals:

await JournalScope.run(recording, () => graph.run(() async { ... }));
//   pushes on entry, pops on exit (success or error)

JournalScope.current          // top of stack, or NullJournal.instance
EffectJournal.current         // the same thing
JournalScope.runSync(journal, body)

Design details worth knowing:

  • The scope does not inherit into spawned tasks. A Future scheduled before the scope exits keeps the zone, but a task spawned in a new zone gets NullJournal — which fails loudly. This is deliberate: an un-journalled effect in a detached task is exactly the bug the design wants surfaced.
  • The ambient journal participates in ledger capture (see §12): the immediate append path sweeps recordsSince(watermark), and the deferred window path relies on operators cooperatively calling LedgerScope.captureEffect.
  • JournalScope.effectiveJournal(captured) prefers the ambient journal when it is not NullJournal — the operator-passed journal: argument is the fallback, so a replay scope always wins over a captured recording journal.

10. The five journalled operators

Cell.asyncMap, Cell.fromStream, Cell.fromFuture, Cell.debounce, and Cell.throttle all take a required journal: parameter. Omitting it is a compile error. The mapper contract for asyncMap is:

final mapped = Cell.asyncMap<int, int>(
  source.cell,
  (v, {required EffectJournal journal}) => journal.io(
    label: 'fetch($v)',
    input: v,
    run: () async => v * 2,        // the actual external call
  ),
  journal: journal,                // the operator's own RecordingJournal
);

Rules that make these replayable:

  • Every observation is routed through the mapper's journal parameter — not through a captured global.
  • On replay the mapper runs again, but journal.io(...) returns the recorded rawOutput and never executes run. This is why replay never touches the network.
  • The operator cooperatively captures each mapper-invocation effect into the active LedgerScope (recordsSince(before) → captureEffect), so the entry that caused the emission carries its effects.
  • fromStream's host is governed with a lifecycle policy; each event journals one I/O record and one policy tick (the the cycle-checker reseed addition — existing tests updated accordingly).
  • debounce/throttle timers go through journal.timer(...); on replay the fire callbacks run in journal order without waiting for real time.

11. The ledger: hash chain, entries, receipts

Genesis

Every chain starts from Ledger.genesisHashOf(graph.id) — the fingerprint of {'graphId': graph.id}. Stores enforce their genesis: Ledger.open and bindLedger throw if the store's genesis does not match the chain's. Ledger.open accepts an explicit genesisHash override for reopening a ledger whose graph is a placeholder (the CLI does exactly this).

What the chain hashes

For each entry:

hash = nextHash(
  prevHash,        // previous entry's hash (genesis for seq 0)
  seq,
  pulseDigest,     // fingerprint(canonical(pulse materialisation))
  receiptDigest,   // fingerprint(canonical receipt JSON)
  effectsDigest,   // fingerprint(effects.toJson())
  deltaDigest,     // fingerprint(deltas.toJson())
  at,              // wall-clock time
)

Ledger.verify() recomputes every hash in one pass and compares prevHash chains; any mismatch throws LedgerIntegrityException(seq, reason).

LedgerEntry

Field Meaning
seq, prevHash, hash chain position
pulseDigest the materialised input pulse
receipt who did what (12 fields, see below)
effects the entry's EffectRecord list
deltas StateDelta list (cellId, before, after, at)
at wall-clock time (forensic; never compared by replay)
receiptCellId the recorded cell id (the replay engine fix: the cell name in the receipt, not the live object's current id)
receiptDigest / effectsDigest / deltaDigest the digested sub-JSONs

The receipt (12 fields)

({
  String id,                    // apply id
  Cell cell,                    // target cell
  Function function,            // the command's function
  ApplyArguments arguments,     // positional/named
  DateTime timestamp,
  int? txSequence,
  bool vetted,
  int? ledgerSeq,               // back-filled by appendInternal
  String? pulseDigest,          // back-filled by appendInternal
  String? receptorVersion,      // the governance layer: '0.0.0' when unversioned
  String? ruleVersion,          // the governance layer
  String? contextVersion,       // the governance layer
})

The three the governance version fields are populated by Ledger.appendInternal from the live nucleus and the cell's DeputyContext; LedgerEntry.fromJson defaults pre--7 ledgers to '0.0.0' (unversioned).

Stores

LedgerStore is the minimal persistence interface: genesisHash, append, lastSeq, lastHash, entriesSince(fromSeq), close. Shipped implementations:

  • InMemoryLedgerStore(genesisHash: ...) — tests and what-if demos.
  • FileLedgerStore.open(path, genesisHash: ...) — JSONL file, each line one canonical entry; holds a RandomAccessFile until close().
  • ForkLedgerStore(record:, inner:) — wraps any store with a synthetic seq-0 ForkRecord entry (a real chain entry hashed with HashChain.nextHash); materialize() writes the synthetic entry into the inner store even before the first real append (the CLI's fork needs a non-empty output file).

Downstream stores must pass test/replay/ledger_store_conformance.dart (§18).

12. LedgerScope: recording coordination

graph.run(body) pushes a LedgerScope zone; every mutation inside is recorded, mutations outside are not (and are the caller's responsibility).

The scope has three capture channels:

  1. Deltas. ValueCell.postProcessRule encodes the before/after values before committing (a non-JSON-encodable payload never reaches the state box) and calls LedgerScope.captureDelta.
  2. Immediate effects. The synchronous mutation path (ValueCell.update, Cell.apply) calls LedgerScope.recordPulse, which sweeps the ambient RecordingJournal's records since a per-scope watermark into the entry. The watermark (a the governance layer fix) is load-bearing: without it, a burst of applies attributes every earlier pulse's records to each later entry.
  3. Deferred windows. The ingress/emit path calls LedgerScope.recordPulseDeferred, which opens a window closed one event-loop turn later so detached operator continuations (asyncMap mappers, debounce fires) can cooperatively LedgerScope.captureEffect their records into the pending entry.

LedgerScope.drain() resolves when every window and the append chain (_tail) have settled; LedgerScope.run drains in its finally.

13. ReplayEngine: replaying a history

final result = await ReplayEngine.replay(
  ledger: ledger,        // the recorded ledger
  target: freshGraph,    // a fresh, un-ledgered graph
  fromSeq: 0,            // start position
  options: ReplayOptions.strict,  // or .diff for diagnostics
);

Per entry, in order:

  1. Refuse a ledgered target — replay reconstructs state; a bound target would mean merging two histories.
  2. Resolve the cell by receiptCellId; unregistered → divergence.
  3. Version check (_checkVersions): the recorded receptorVersion/ruleVersion must be satisfied by the graph's VersionRegistry, or by the live implementations matching exactly. Unversioned ledgers (null versions) replay only against unversioned targets — refusing to guess is the design.
  4. Reconstruct the pulse (PulseReconstructor): the first positional receipt argument becomes the payload (Pulse<dynamic>(args.first, source: cell)); if there are no arguments, the entry's own delta's after is used. Hand-crafted entries without either diverge.
  5. Dispatch inside JournalScope.run(ReplayJournal(entry.effects)); settleAfterDispatch (default true) drains the microtask queue so asynchronous receptor continuations finish before the checks.
  6. assertExhausted — the receptor must have consumed exactly the recorded effects, in order, with matching labels and inputs.
  7. Delta verification — for every recorded delta, the target cell's current value must equal delta.after (compared as canonical JSON).

ReplayResult carries success, entriesReplayed, and divergences (a list of DivergenceReport).

ReplayOptions

Option Default Meaning
failOnDivergence true Throw on the first divergence (strict); false collects and continues (diff)
verifyReceipts true Verify back-filled ledgerSeq/pulseDigest; disable only for hand-built entries
settleAfterDispatch true Settle the microtask queue before journal/delta checks
maxEntries null Replay only a prefix

ReplayOptions.strict is the production default; ReplayOptions.diff is the diagnostic preset used by CLI-style tools.

14. Divergence reporting

Three layers of diagnostics:

  1. ReplayDivergenceException — thrown synchronously by the journal or the engine (when failOnDivergence); carries message, ordinal, seq, and report.
  2. DivergenceReport — seq, expected, actual, lastEffect (the effect consumed immediately before the divergence), reason.
  3. ReplayResult.divergences — the full list when running in diff mode.

A good report reads like a mini-post-mortem:

DivergenceReport(seq: 2, expected: version 1.0.0 / 1.0.0,
  actual: version 2.0.0 / 2.0.0,
  reason: version boundary: the ledger recorded receptor version 1.0.0 …

15. Forking: what-if branches

A fork is a new ledger whose chain genesis is the fingerprint of a ForkRecord, and whose history is bound to the parent's hash at the fork point.

final fork = await graph.fork(
  parent: ledger,
  atSeq: 5,                      // parent sequence
  buildFreshGraph: () {          // fresh cells, same names
    CellGraphRegistry.forceReset();
    final fresh = Cell.state<int>(initial: 0);
    return (CellGraph.builder(graphId: 'g')
          ..registerState('counter', fresh))
        .build();
  },
  buildStore: (genesis) =>       // store factory, not a store
      InMemoryLedgerStore(genesisHash: genesis),
  policy: ForkPolicy.isolated,   // the only the fork engine policy
);

Key semantics:

  • ForkRecord = forkId, originalLedgerId, divergedAt, originalSnapshotHash, parentHeadHash, at. genesisHash is the fingerprint of everything except at — the fork chain is distinguishable from the parent's.
  • Baseline replay. The fork does not copy state; it replays parent entries 0..atSeq into the fresh graph, so the fork's working state is the parent's state after seq atSeq.
  • divergedAt + 1. ReplayEngineFork.replayFork(fork:, mutation:) replays from the parent's divergedAt + 1 onward. atSeq == 0 means the baseline is the state after the parent's first entry.
  • Mutation. typedef Mutation = Pulse? Function(LedgerEntry entry, Pulse pulse); — return a replacement Pulse to substitute, return null to drop the entry (the fork's ledger then has no record of it), return the same pulse to keep it.
  • The fork writes its own ledger. Each replayed entry is appended to fork.ledger; deltas are not compared against the parent's because a fork is expected to diverge — the fork's ledger records what the fork actually did.
  • Only ForkPolicy.isolated ships. sharedTopology and dropUnreached require a later revision snapshot reconstruction and throw UnimplementedError.

Verifying a fork

fork.verify() (the ForkVerify extension on ForkHandle) checks, in order: the parent chain, the fork chain, and the genesis binding — ForkRecord.parentHeadHash must equal the parent's hash at divergedAt (ForkParentLookup.hashAtSeq). A fork whose binding does not match is stale or forged: ForkIntegrityException.

16. Governance: versions, registry, translators

Where versions live

  • Receptor.version and TestCell.version default to '0.0.0' (unversioned); custom implementations may override.
  • DeputyContext.version defaults to '1.0.0'; DeputyContext.system is '0.0.0'. Mandate.version is a static pillar — it cannot be evolved by a deputy, because it declares the schema of the mandate itself.
  • Every entry's receipt records the three versions that produced it.

VersionRegistry — graph-scoped, on purpose

graph.versions.register(
  cellId: 'admin',
  version: '1.0.0',
  receptor: myV1Receptor,
  testRule: myV1Rule,           // both must report version '1.0.0'
);
graph.registerVersion('admin'); // registers the live pair at its own version

The registry is per-graph via an Expando (CellGraphVersions.versions) — deliberately not process-wide: two graphs in one process may have the same cell name with different version histories, and a process-wide table would let one graph's versions shadow the other's. Registering the same (cellId, version) twice with a different implementation throws; identical re-registration is a no-op.

The engine's decision

For each entry: if the graph's registry has the recorded version, replay proceeds. Otherwise the live receptor and rule must match exactly. Otherwise — a loud DivergenceReport with the recorded and live versions. An unversioned ledger replays only against an unversioned target.

ContextTranslator

A context schema change is the caller's semantic domain; the framework provides the boundary:

class V1ToV2 implements ContextTranslator {
  @override
  String get fromVersion => '1.0.0';
  @override
  String get toVersion => '2.0.0';
  @override
  FutureOr<DeputyContext> translate(DeputyContext source) =>
      DeputyContext(
        baseContext: Context.system,
        authority: 'UPDATE',
        version: '2.0.0',
        // …translate the v1 fields…
      );
}

graph.translators.register(V1ToV2());      // CellGraphTranslators
await graph.translators.translate(v1ctx, target: '2.0.0');

ContextTranslatorRegistry.translate returns the source unchanged when the versions are equal, throws UnimplementedError when no translator exists (the loud failure the exit criteria require), and verifies the translator's output version. the governance layer registers the machinery and enforces the boundary; wiring translators into the engine dispatch loop is the deferred a later governance revision item.

Purity dispatch (TestCellReplay)

The receptor pipeline no longer calls the rule directly. It calls TestCellReplay.invoke(rule:, object:, host:, journal:, ruleLabel:):

  • pure → rule.call(...) — synchronous rules stay synchronous (the framework's pulse contract depends on it).
  • readOnlyExternal → rule.call(...) with the journal in scope, then a cooperative sweep hands records the rule wrote to the LedgerScope (the the journal asyncMap pattern).
  • effectful → journal.verdict(...); the rule runs once on the recording side and never on the replay side.

The rule label is conventionally ${rule.runtimeType}@${rule.version} and is validated by the replay journal, so a changed rule diverges by label even before the version check runs.

17. Visualisation and the CLI

In-library visualisation

final graphMermaid = graph.visualise();          // CellGraphVisualise
final ledgerMermaid =
    await ledger.visualise(format: 'mermaid', mode: 'deltas');
final ledgerDot = await ledger.visualise(format: 'dot', mode: 'cells');

mode: 'deltas' is the forensic view (what changed, in order); mode: 'cells' is the topology view (who participated). The delta renderer tracks the previous delta node instead of assuming every entry has one — the fork's synthetic seq-0 entry, and hand-crafted entries, have none.

The cell-replay CLI

cell-replay verify    --ledger <path> [--format human|json]
cell-replay diff      --ledgerA <path> --ledgerB <path> [--format human|json] [--maxDiffs N]
cell-replay fork      --ledger <path> --at <seq> --out <path> [--format human|json]
cell-replay visualise --ledger <path> [--mode deltas|cells] [--format mermaid|dot]
cell-replay inspect   --ledger <path> [--format human|json]

Exit codes: 0 success · 1 verification failure / diff found · 2 usage error · 3 internal error. dart run bin/cell_replay.dart --help prints the usage text.

Two CLI scope decisions worth internalising:

  • verify checks the chain only. --graph is rejected (planned CLI work needs a later revision snapshot reconstruction). The chain guarantee is real: it proves no byte of history was altered after recording.
  • The genesis compromise. A ledger file does not carry its genesis; the CLI reads the first entry's prevHash and trusts it. A ledger whose first entry was tampered would pass genesis binding — this is documented in the help text and fixed by a future --genesis flag flag.
  • fork writes the ForkRecord genesis, no entries after it. --replaceSeq (fork-with-replay) is planned CLI work.

inspect prints the human summary (entries, deltas, cells, span) or canonical JSON; visualise output pastes directly into GitHub/Notion markdown.

18. The conformance suite and the determinism gate

Ledger-store conformance

test/replay/ledger_store_conformance.dart is the acceptance criterion for any downstream store (Postgres, S3, …):

runLedgerStoreConformance(
  'MyStore',
  () => MyStore(genesisHash: 'test-genesis'),
  isDurable: true,                    // survives reopen
  fresh: () { /* allocate a NEW resource per test */ },
);

It exercises append/lastSeq, out-of-order rejection, genesis binding, entriesSince ordering, close semantics, and (durable only) reopen. The fresh hook matters: the suite opens the factory once per test — a durable store must reopen the same data within a test but a fresh resource across tests.

The determinism gate

dart run tool/replay_determinism_check.dart

Runs test/replay twice, normalises the JSON reporter on (test name, result, message), and fails when the two runs disagree. A test whose output varies across runs is either non-deterministic by design (mark it @Skip with a comment) or is doing real DateTime.now() / Random() work that would make the ledger itself non-reproducible.

The three demos

dart run example/replay/record_and_replay.dart   # file ledger, reopen, replay
dart run example/replay/whatif_branch.dart       # fork + replace a pulse
dart run example/replay/audit_ledger.dart        # the auditor's workflow

Part IV — Recipes

R1. Record and replay a state cell

See Part II. The essential beats: register, bind with Ledger.genesisHashOf, mutate inside graph.run, verify, rebuild fresh, ReplayEngine.replay.

R2. An effectful mapper

final source = Cell.state<int>(initial: 0);
final graph = (CellGraph.builder(graphId: 'r2')
      ..registerState('src', source))
    .build();

final journal = RecordingJournal();      // lives as long as the operator
final mapped = Cell.asyncMap<int, int>(
  source.cell,
  (v, {required EffectJournal journal}) => journal.io(
    label: 'double($v)',
    input: v,
    run: () async => v * 2,
  ),
  journal: journal,
);

final ledger = await graph.bindLedger(
  store: InMemoryLedgerStore(
    genesisHash: Ledger.genesisHashOf(graph.id),
  ),
);
// Effects are records: the recording runs inside a journal scope.
await JournalScope.run(journal, () => graph.run(() async {
  source.update(1);
  source.update(2);
}));

Replay into a fresh graph built the same way; the mapper re-runs but run never executes — rawOutput is served. If the replay mapper were changed, the entry's I/O record would diverge on label or inputDigest.

R3. Debounce replay

final source = Cell.state<int>(initial: 0);
final debounced = Cell.debounce(
  source.cell,
  const Duration(milliseconds: 50),
  journal: RecordingJournal(),
);
// …bind, run, emit bursts…

On replay, ReplayJournal.timer validates the scheduled duration and input, then fires onFire in journal order after one microtask — the same ordering trick that lets a superseded debounce be cancelled before its fire callback runs. No real timers are waited on.

R4. A custom receptor with purity and version

class DoublingReceptor extends ReceptorBase<Cell> {
  @override
  String get version => '1.0.0';

  @override
  Receptor<Cell> get clone => DoublingReceptor();

  // Override call/validation to transform the pulse; the base class
  // handles the governance gates. Keep it pure: the transform is a
  // function of the pulse.
}

final cell = Cell.governed(receptor: DoublingReceptor());

Rules: declare purity (default pure is fine here), stamp a version if the implementation may ever change, and register the graph (graph.registerVersion('c') registers the live pair). The ledger then records receptorVersion: '1.0.0' per entry; replay against a 2.0.0 build fails loudly until the graph's VersionRegistry has the recorded version.

R5. An effectful test rule

class SendNotificationRule extends TestCell<Cell> with Effectful {
  @override
  String get version => '1.0.0';
  SendNotificationRule() : super((pulse, {host, arguments, user}) {
    // The rule runs exactly once, on the recording side only.
    return pulse.payload != null;
  });
}

final src = Cell.ingress<int>(testRule: SendNotificationRule());
final graph = (CellGraph.builder(graphId: 'r5')
      ..register('src', src.cell))
    .build();
final ledger = await graph.bindLedger(
  store: InMemoryLedgerStore(
    genesisHash: Ledger.genesisHashOf(graph.id),
  ),
);
final recording = RecordingJournal();
await JournalScope.run(recording, () => graph.run(() async {
  src.emit(1);
}));
final entry = await ledger.entriesSince(0).first;
print(entry.effects.single.runtimeType);   // VerdictEffect

On replay, TestCellReplay.invoke routes through journal.verdict: the recorded decision is served, the rule body never runs. Changing the rule body without changing its version diverges on the verdict input or the rule label.

R6. A readOnlyExternal test rule

class FeatureFlagRule extends TestCell<Cell> with EffectfulReadOnly {
  @override
  String get version => '1.0.0';
  FeatureFlagRule() : super((pulse, {host, arguments, user}) {
    return EffectJournal.current.io<bool>(
      label: 'flag(${pulse.payload})',
      input: pulse.payload,
      run: () async => true,   // the real read; replay serves it
    );
  });
}

The rule re-runs during replay; its read is served from the journal. The returned value is the recorded rawOutput, so the replay decision matches the recording's — provided the order of reads is unchanged.

R7. EphemeralPolicy ticks (the C4 fix)

var ticks = 0;
final policy = EphemeralPolicy<Cell>(
  eventLimit: 100,
  onEvent: (object, {required cell, required policy, arguments, user}) {
    ticks++;
    return (events: policy.events + 1);
  },
  onInvalidate: (nucleus) => true,
);
final cell = Cell.governed(ephemeralPolicy: policy);
final graph = (CellGraph.builder(graphId: 'r7')
      ..register('c', cell))
    .build();
final ledger = await graph.bindLedger(
  store: InMemoryLedgerStore(
    genesisHash: Ledger.genesisHashOf(graph.id),
  ),
);
final recording = RecordingJournal();
await JournalScope.run(recording, () => graph.run(() async {
  await cell.apply<Pulse<int>>((
    function: (int payload) => Pulse<int>(payload),
    arguments: (
      positionalArguments: [1],      // arguments-first reconstruction
      namedArguments: null,
    ),
    compensation: null,
  ));
}));
final entry = await ledger.entriesSince(0).first;
print(entry.effects.single.runtimeType);   // PolicyTickEffect

Replay consumes the tick and validates (policyLabel, cellId, input) in order; the policy callback is not re-invoked (so the tick count is zero on replay — the recorded tick is the history). A tick-order mismatch is a ReplayDivergenceException with the offending ordinal. This is what closes the cycle-checker concern: a diamond graph can no longer trip the CycleChecker spuriously during replay, because the tick order is journaled.

R8. Fork and mutate

// Parent: update(1), update(2), update(3) → value 3.
final fork = await graph.fork(
  parent: ledger,
  atSeq: 1,                        // baseline = state after seq 1 (2)
  buildFreshGraph: () {
    CellGraphRegistry.forceReset();
    final fresh = Cell.state<int>(initial: 0);
    return (CellGraph.builder(graphId: 'r8')
          ..registerState('counter', fresh))
        .build();
  },
  buildStore: (genesis) => InMemoryLedgerStore(genesisHash: genesis),
);

final result = await ReplayEngineFork.replayFork(
  fork: fork,
  mutation: (entry, pulse) {
    if (entry.seq == 2) return Pulse<int>(30, source: pulse.source);
    return pulse;                  // keep the rest; null would drop
  },
);
final forkValue =
    (fork.graph['counter']!.cell as ValueCell<int>).value; // 30

Remember: Cell.state replaces on update, so the arithmetic above gives 2 (baseline) → 30 (mutated seq 2). The fork's own ledger contains the fork record plus the entries the fork actually replayed.

R9. Verify a fork

await fork.verify();               // ForkVerify: parent + fork + binding
final boundHash = await ledger.hashAtSeq(fork.record.divergedAt);
print(boundHash == fork.record.parentHeadHash);   // true

fork.verify() throws ForkIntegrityException if the parent is corrupt, the fork chain is corrupt, or the recorded parentHeadHash does not match the parent's hash at divergedAt. This is the check that separates a fork from a fabrication.

R10. A version boundary with a translator

// Recording: a DeputyContext at mandate version 1.0.0.
final v1 = DeputyContext(
  baseContext: Context.system,
  authority: 'UPDATE',
  version: '1.0.0',
);
// …cells created under v1, ledger recorded…

// Replay target: the same graph shape, but the live context is v2.
final registry = graph.translators;         // ContextTranslatorRegistry
registry.register(V1ToV2());                // see §16
final v2 = await registry.translate(v1, target: '2.0.0');

// Without the translator, translate() throws UnimplementedError —
// the boundary is loud by design.

The engine's version check is about receptor/rule versions; context versions ride in the receipt and are the translator's domain. Keep both stories separate when diagnosing: a version boundary divergence names the receptor and rule versions; a missing ContextTranslator names "from" -> "to".

R12. Reading a divergence report

A DivergenceReport is read top-down: seq locates the entry, reason names the failure class, expected/actual are the compared values, and lastEffect shows the last journal record consumed before the failure.

Reason signature What actually happened Where to look
version boundary: … Recorded receptor/rule versions unsatisfied VersionRegistry, live version overrides
journal not exhausted: … Receptor consumed fewer effects than recorded Rule/receptor changed; check purity dispatch
effect kind mismatch … expected TimerEffect, recorded IoEffect Effect order changed Receptor/operator refactor
I/O label mismatch: expected "fetch(1)", recorded "fetch" Label construction changed Operator mapper
verdict rule label mismatch … Rule class/version string changed TestCell rule
policy tick … mismatch Policy tick order/policy/cell/input changed EphemeralPolicy wiring
pulse could not be reconstructed … Entry has no arguments and no deltas Hand-crafted entries
ledger delta refers to cell "x", which is not registered … Target graph shape differs Registration
cell "x" delta mismatch: expected …, actual … State diverged after a successful dispatch Non-journalled side effect inside the rule

Part VII — Scope, deferred work, and migration

Shipped

Codecs and fingerprints; stable identity and graphs; the full EffectJournal machinery and the five journalled operators; ledgers, delta capture, hash chains and file persistence; the replay engine with divergence diagnostics; isolated forks with mutations and fork verification; governance versions, the version registry, context translators, purity dispatch and policy-tick journaling; the cell-replay CLI, visualisation, the conformance suite, the determinism gate, the guide and the three demos.

Deferred, with the work that unblocks each

  • Snapshot reconstruction. CellGraphSnapshot exists and round-trips, but rebuilding a live CellGraph from a snapshot needs per-cell factories. Unblocks verify --graph and the non-isolated fork policies.
  • Translator dispatch and apply-path verdicts. Wiring ContextTranslator into the engine's dispatch loop, and journaling TestActionRule verdicts on the apply path.
  • CLI completion. --genesis (replacing the first-entry trust), verify --graph, fork --replaceSeq/--replacePayloadJson, visualise --mode pulses.
  • Migration (future). Replay across graph shape changes is a migration problem: translating receptors, renaming cells, and re-binding identities. The version machinery (the governance layer) is the foundation migration will build on.

The boundary line, one more time

The caller knows how to rebuild the graph; the framework knows how to rebuild the state.
