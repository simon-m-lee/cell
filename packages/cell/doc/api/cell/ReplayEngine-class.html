ReplayEngine

ReplayEngine class

The replay engine.

Given a Ledger and a CellGraph (the "target", typically freshly built from the same CellGraphBuilder that produced the original), the engine replays entries one by one, dispatching each reconstructed pulse into the target graph and asserting that the resulting state matches the ledger entry's recorded deltas.

Non-obvious: the target graph is provided, not reconstructed

The engine does not reconstruct a graph from a CellGraphSnapshot — that is a later revision (a payload-codec-driven concern; the current The snapshot does not store enough to rebuild a graph's cells from scratch without the payload-codec registry). The caller provides the target graph, typically freshly built from the same CellGraphBuilder that produced the original. The design's exit criterion "replay 500 pulses against an identical graph" describes exactly this: the target is the same graph shape, not a reconstructed one. A later revision will relax this, and the ReplayEngine API does not need to change.

What is verified per entry

  1. The receipt's back-filled fields (ledgerSeq, pulseDigest).
  2. The receipt's cell is registered in the target graph.
  3. The pulse is reconstructable (arguments, or a recorded delta).
  4. The receptor consumes exactly the entry's recorded effects, in order, through the per-entry ReplayJournal (the target's effectful operators consult the ambient journal — see JournalScope.effectiveJournal).
  5. Every recorded StateDelta is reproduced: after dispatch, each delta cell's current value must equal delta.after.

What is deliberately not verified: the recorded pulseDigest against a reconstructed pulse. The digest hashes the pulse's full JSON including its wall-clock timestamp; a hash is one-way and a reconstruction can never match it byte-for-byte. The delta comparison is the authoritative state check. (The engine design's step 9 check would fail on every entry; this engine documents that honestly instead.)
