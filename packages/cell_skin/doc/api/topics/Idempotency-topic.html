HowTo-Idempotency

Timeouts, retries, and double-applies are the operational holes in any command surface. cell_skin's correlation model closes them: a retried command either returns its original outcome or never executes twice.

The correlation model

  • WireRequest.correlationId — server-assigned. Transport adapters generate it; waiters match on it exclusively.
  • WireRequest.clientCorrelationId — the caller's id, echoed verbatim on the response/error. Nobody matches on it — a client can never hijack another client's pending response.
final request = WireRequest(
  cellId: 'home.living.thermostat',
  function: 'setTarget',
  positional: {'0': 21},
  correlationId: 'srv-7',        // generated by the transport
  clientCorrelationId: 'retry-key-1', // your id — echoed, never matched
);

The idempotency store

The router keeps a bounded (256-entry) store keyed by clientCorrelationId ?? correlationId. A duplicate key replays the stored outcome — re-wrapped with the current request's correlation ids, so the retry's waiter always matches its own reply. The command function does not run again.

This is why SkinClient and RemoteCellClient correlation ids carry monotonically increasing counters — collisions cannot happen by accident.

Timeout → retry without double-apply

The REST adapter surfaces membrane timeouts as 504 outcome_unknown — the command may have committed. Retry the same correlationId:

curl -X POST http://127.0.0.1:<port>/skin/apply \
  -H 'Content-Type: application/json' \
  -d '{"cellId":"home.living.thermostat","function":"setTarget",
       "positional":[21],"correlationId":"retry-key-1"}'

If the first apply committed, the retry returns the stored outcome (200) without executing again. If the timeout was real, the retry is a fresh command under the same key.

What is not idempotent

  • A brand-new clientCorrelationId per retry — that is a new logical call and will execute again. Reuse the id for retries.
  • SkinClient.apply generates a fresh id per call by design; build the retry id yourself (e.g. one id per user action, stored until the outcome is confirmed).

The 256-entry bound

The store drops the oldest entry past 256 keys. For long audit windows, treat the ledger (reachable via GET /skin/ledger) as the source of truth — the idempotency store is a retry convenience, not the audit trail.
