# HowTo-Idempotency

Timeouts, retries, and double-applies are the operational holes in any
command surface. cell_skin's correlation model closes them: a retried
command either returns its original outcome or never executes twice.

## The correlation model

- `WireRequest.correlationId` — **server-assigned**. Transport
  adapters generate it; waiters match on it exclusively.
- `WireRequest.clientCorrelationId` — the caller's id, echoed
  verbatim on the response/error. Nobody matches on it for delivery — a
  client can never hijack another client's pending response.

```dart
final request = WireRequest(
  cellId: 'home.living.thermostat',
  function: 'setTarget',
  positional: {'0': 21},
  correlationId: 'srv-7',        // generated by the transport
  clientCorrelationId: 'retry-key-1', // your id — the retry key
);
```

## The idempotency store

The router consults an `IdempotencyStore` (default:
`MemoryIdempotencyStore` — 1024 completed records, 24 hour TTL). The
store key is **the request actor plus**
`clientCorrelationId ?? correlationId`; the fingerprint is the SHA-256
of `cellId`, function, positional/named arguments, and `lastSeenSeq`.

| Second call, same key | Result |
| :--- | :--- |
| Same fingerprint | The stored `ApplyAccepted`/`ApplyStaged` replays — re-wrapped with the *current* request's correlation ids, so the retry's waiter always matches its own reply. The command does not run again, and `lastSeq` does not move. |
| Different fingerprint | `WireError{code: 'idempotency_conflict'}` (HTTP 409, distinct from the cursor `conflict`). The function is not called; the stored record is kept. |
| First attempt still in flight | The second call waits for that attempt, then replays it. |

Only `ApplyAccepted` and `ApplyStaged` are stored. A domain
`ApplyRejected`, a cursor miss, `bad_arguments`, `unknown_tool`, or a
`transport_error` aborts the claim — nothing is cached — so a retry
after the occupant leaves, or after the ledger head moves, is a new
apply that can succeed. A `queue_timeout` (see `HowTo-RestAdapter.md`)
is likewise not a stored outcome; a retry may run.

Pass a durable store to keep replays across restarts:

```dart
import 'package:cell_skin/cell_skin_io.dart';

final store = await FileIdempotencyStore.open(
  directory: './skin-idem', // the app picks the directory, never the skin
  maxEntries: 1024,
  ttl: const Duration(hours: 24),
  lease: const Duration(minutes: 2),
);

final membrane = await SkinMembrane.open(
  graph: graph,
  bindings: bindings,
  idempotency: store,
  // ...
);
```

`FileIdempotencyStore` implements the same `IdempotencyStore` interface
as the memory store. One log file, one canonical-JSON record per line,
rewritten under an exclusive file lock (`directory/lock`) after every
mutation. The in-flight lease is two minutes by default: within one
process a live lease makes later claimers `IdempotencyWait`; across
processes the next `claim` after `leaseUntil` returns `IdempotencyOwned`.
A crash after the domain commit and before `complete` can still
double-apply — `complete` is what makes the retry safe. A strict-receipt
failure that appended rows persists its `errorCode`/`errorMessage` on
the line, so the replay is the same `transport_error`, never a fake
success. The file never stores `liveOutcome`, so a replayed record has
only `outcomeJson`; `SkinClient.apply` throws `outcome_json_only` for
it — use `SkinMembrane.request` (or REST, which already prefers
`outcomeJson`) to read the wire form.

## Timeout → retry without double-apply

The REST adapter surfaces membrane timeouts as
`504 outcome_unknown` — the command may have committed. Retry the
**same** `correlationId`:

```bash
curl -X POST http://127.0.0.1:<port>/skin/apply \
  -H 'Content-Type: application/json' \
  -d '{"cellId":"home.living.thermostat","function":"setTarget",
       "positional":[21],"correlationId":"retry-key-1"}'
```

If the first apply committed, the retry returns the stored outcome
(`200`) without executing again. If the timeout was real, the retry is
a fresh command under the same key. Without a durable store, the replay
exists only in this process, until the record expires — check
`/skin/ledger` for the truth.

## What is *not* idempotent

- A brand-new `clientCorrelationId` per retry — that is a new logical
  call and will execute again. Reuse the id for retries.
- `SkinClient.apply` generates a fresh id per call by design; build the
  retry id yourself (e.g. one id per user action, stored until the
  outcome is confirmed).
- A different body under the same id — that is `idempotency_conflict`,
  deliberately.

## The 1024-entry bound and the TTL

The memory store drops the oldest completed record past 1024 keys and
expires records after 24 hours (expired records are swept on `claim`
and `complete`, so they never occupy the cap). Replay is
**at-least-once at the edges**: past the TTL, or once the oldest record
is evicted from a full store, a retry with the same id is a new apply.
For long audit windows, treat the ledger (reachable via
`GET /skin/ledger`) as the source of truth — the idempotency store is a
retry convenience, not the audit trail, and not an exactly-once
guarantee.
