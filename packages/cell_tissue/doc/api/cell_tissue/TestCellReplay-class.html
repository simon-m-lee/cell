TestCellReplay

TestCellReplay class abstract final

Purity-aware invocation of a TestCell.

How it works

The governance layer checks the rule's purity and routes accordingly:

  • Purity.pure — call the rule. Its decision is a function of its input; replay re-computes it exactly.
  • Purity.readOnlyExternal — call the rule inside a journal scope. Its decision is re-computed, but its observations are served from the journal.
  • Purity.effectful — do not call the rule on replay; consume its recorded VerdictEffect. On the recording side the rule runs once inside journal.verdict and its decision is journaled. If the replay journal has no verdict for the current input, the journal throws ReplayDivergenceException — the rule changed since the recording.

Non-obvious: where the version dispatch lives

This class dispatches on purity only. The receptor/rule version boundary is enforced one level up, by ReplayEngine._checkVersions before any dispatch happens: the recorded versions must be satisfied by the graph's VersionRegistry or by the live implementations matching exactly — otherwise the engine reports a divergence without calling the rule at all.

See also:

  • EffectJournal.verdict — the journal primitive this wraps.
  • VersionRegistry — the version boundary one level up.
