TestRule

TestRule<C> class

The foundational abstraction for Validation Logic, Policy Enforcement, and Security Guarding within the reactive framework.

A TestRule defines a boolean predicate that determines whether a specific operation, state transition, or data payload is permissible within a given host environment. It acts as an Integrity Gate for the reactive graph, ensuring all mutations maintain structural and business invariants.

Developer Ergonomics: Intuitive Orchestration

The Cell Framework is architected with a human-first approach. Human developers can define validation rules using simple, intuitive function signatures and compose them using the + operator, creating clear, readable validation pipelines.

// Simple validation rule
final isPositive = TestRule<int>((object, {host, arguments, user}) {
  return object > 0;
});

// Rule with host context
final isAllowed = TestRule<Cell>((object, {host, arguments, user}) {
  final ctx = host?.context;
  return ctx?.domains?.contains('Finance') ?? false;
});

// Composition
final combined = isPositive + isAllowed + isInRange;

1. Architectural Role: Decoupling Logic from State

The primary role of TestRule is to decouple Validation Constraints from State Management. In this architecture, state containers (like Cell) are not burdened with the specific implementation of their constraints. TestRule provides a standardized interface for defining Business Invariants that can be composed, inherited, and executed across any layer of the system.

2. Developer Ergonomics & Human Legibility

Human developers define rules using simple function signatures:

// 1. Range validation
final rangeRule = TestRule<int>((object, {host, arguments, user}) {
  return object >= 0 && object <= 100;
});

// 2. Pattern validation
final emailRule = TestRule<String>((object, {host, arguments, user}) {
  return RegExp(r'^[^@]+@[^@]+\.[^@]+$').hasMatch(object);
});

// 3. Context-aware validation
final adminRule = TestRule<Cell>((object, {host, arguments, user}) {
  final ctx = host?.context;
  return ctx?.stakeholders?.contains('Admin') ?? false;
});

// 4. Using user data for configuration
final thresholdRule = TestRule<int>((object, {host, arguments, user}) {
  final limit = user as int? ?? 100;
  return object <= limit;
}, user: 50);

3. Core Architectural Patterns:

A. The Chain of Responsibility (Composition)

TestRule is designed for Atomic Composition. Using the + operator, individual rules are combined into a Validation Pipeline. This follows the Chain of Responsibility pattern, where a proposed state change must satisfy every rule in the sequence to be committed.

final pipeline = isPositive + isInRange + isAuthorized;
// All rules must pass for validation to succeed

B. Hybrid Convergence (Sync/Async)

To support high-performance reactive waves alongside complex I/O-bound security checks, TestRule utilizes FutureOr.

  • Synchronous Path: Simple checks (e.g., range validation) resolve immediately, minimizing latency in the Digital Organism.
  • Asynchronous Path: Complex checks (e.g., database lookups or Deputy Mandate verification) resolve via Future, maintaining Causal Integrity across the event loop.
final asyncRule = TestRule<Cell>((object, {host, arguments, user}) async {
  final result = await database.checkAuthorization(object);
  return result;
});

C. Operational Resilience (Fail-Safe Execution)

To prevent validation logic from stalling the reactive graph, unhandled exceptions within a rule's execution are treated as a Pass (true). This Fail-Safe philosophy ensures that a faulty validator does not paralyze the system, while still allowing for diagnostic auditing.

D. Memory Efficiency (Flyweight Pattern)

To support high-density reactive networks, rules utilize the Flyweight Pattern. Rule configurations are stored in memory-optimized Dart Records, minimizing the heap footprint of validation chains even at massive scale.

4. Example: E-Commerce Validation Pipeline

// Step 1: Validate positive quantity
final positiveQuantity = TestRule<int>((object, {host, arguments, user}) {
  return object > 0;
});

// Step 2: Validate within stock
final inStock = TestRule<int>((object, {host, arguments, user}) {
  final stock = (host as InventoryCell).stock;
  return object <= stock;
});

// Step 3: Validate user authorization
final isAuthorized = TestRule<Cell>((object, {host, arguments, user}) {
  final ctx = host?.context;
  return ctx?.domains?.contains('Inventory') ?? false;
});

// Combine into a validation pipeline
final orderValidation = positiveQuantity + inStock + isAuthorized;

// Use in a cell
final inventoryCell = Cell(
  testRule: orderValidation,
  receptor: Receptor((cell, pulse, {user}) {
    // Only executed if validation passes
    return pulse;
  }),
);

5. Performance Considerations

  • Short-Circuit: If any rule returns false, validation stops immediately
  • Async Rules: Async rules suspend the pipeline, which may impact performance
  • Composition: Deeply nested chains may have overhead; keep them shallow
  • Shared Rules: Rules are stateless and can be shared across cells

Type Parameters:

  • C: The Host Environment type. This binds the rule to a specific node context, allowing for cross-field validation while ensuring type safety across the reactive graph.
