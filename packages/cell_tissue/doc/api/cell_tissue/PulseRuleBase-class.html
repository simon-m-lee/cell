PulseRuleBase

PulseRuleBase<C extends Cell, I extends Pulse, O extends Pulse> class abstract

The foundational implementation and architectural base for all PulseRule variants.

PulseRuleBase provides the common infrastructure for defining, composing, and executing transformation logic within the reactive graph. It is engineered for High-Performance Composition, allowing complex processing pipelines to be built from simple, discrete functional units.

1. Architectural Role: The Logic Unit

In the cell.core ecosystem, a pulse rule is the atomic unit of transformation. PulseRuleBase orchestrates the lifecycle of these units:

  • Encapsulation: It wraps a standard Dart function into a formal reactive contract, providing the necessary signatures to interact with a Cell and its Pulse stream.
  • Composition Engine: It implements the + operator, enabling the Chain of Responsibility pattern. Rules can be sequentially linked into a PulseRuleChain where the output of one rule becomes the input for the next.
  • Metadata Attachment: It facilitates the inclusion of arbitrary user data, allowing logic to be parameterized without altering the functional signature of the rule.

2. Memory Optimization: The Record Pattern

To support systems with millions of reactive nodes, this class utilizes the framework's Flyweight Strategy:

  • Sparsity-Aware Storage: Configuration data (the function and metadata) is packed into a compact, internal Record.
  • Zero-Tax Defaults: If no metadata is provided, the record shape is automatically optimized to omit the field, reducing the memory footprint of the rule instance in the heap.
  • Const-Ready Design: The base is designed to be const, ensuring that identical rules share the same physical memory address across the entire application.

3. Functional Mechanics: Resilient Execution

The primary entry point for a rule is the call method, which implements a Safe-Harbor Execution model:

  1. Contextual Awareness: The rule is executed with full access to the host Cell and the triggering Pulse, allowing for state-aware transformations.
  2. Error Isolation: Transformations are wrapped in an internal error boundary. If a custom rule function throws an exception, the framework catches it and fallbacks to the original pulse. This ensures that a local logic error in a specific cell does not terminate the broader "Reactive Wave."
  3. Type Integrity: The base ensures that the output of the transformation matches the expected pulse type O, discarding incompatible results to maintain graph-wide type safety.

4. Usage in Receptors

PulseRuleBase is the engine behind Receptor logic. Whether performing a simple value mapping or a complex security filter, receptors rely on the resilience and composability provided by this base class to navigate the reactive pulse chain.

Type Parameters:

  • C: The type of the host Cell (the transformation target).
  • I: The type of the incoming Pulse (the input).
  • O: The type of the resulting Pulse (the output).
