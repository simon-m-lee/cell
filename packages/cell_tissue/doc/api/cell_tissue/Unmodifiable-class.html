Unmodifiable

Unmodifiable class abstract

A specialized Marker Interface used to identify cell variants and data structures that have been locked against external mutation.

In the cell.core framework and the wider Cell Framework Ecosystem (including cell_tissue, cell_organ, etc.), reactive nodes frequently exist in two distinct states: a Principal (mutable) form and a Deputy (restricted) form. Unmodifiable serves as the primary architectural indicator that a specific instance is a Read-Only View, ensuring data integrity by preventing unauthorized imperative changes.

1. Architectural Role: The Deputy Pattern

The Unmodifiable contract is a cornerstone of the Deputy Pattern. It allows a mutable node—such as a ValueCell or other reactive entity—to be safely exposed to downstream observers (e.g., a UI layer or a third-party module) without granting those observers the authority to trigger state updates.

  • Mutation Blocking: Operations that attempt to alter state (such as trigger, apply, or collection modifiers like add) are designed to check for this interface. If present, the operation is categorically rejected or neutralized by the cell's security policy.
  • Reactive Continuity: Being Unmodifiable does not stop a cell from being reactive. An unmodifiable cell remains a live participant in the graph; it will still emit signals and update its internal value if its underlying principal changes. It simply blocks mutations initiated directly through its own handle.

2. Ecosystem Integration

This interface is utilized across specialized ecosystem libraries to enforce consistent security semantics:

  • cell_tissue: Identifies read-only views of reactive lists, maps, and sets where structural modification is prohibited.
  • cell_organ: Marks entities in a relational graph as immutable projections, preventing accidental edits to database-backed models.
  • cell.core: The foundational marker for ValueCell deputies created via the .unmodifiable property.

3. Design & Performance Characteristics

  • Identity Transparency: In many implementations, an unmodifiable deputy shares the same physical storage and synchronization lock as the principal. This ensures Zero-Copy Projection—no additional memory is wasted on data duplication.
  • Capability-Based Security: By wrapping a principal cell in an Unmodifiable deputy, the framework strips away the "Write" capability while retaining the "Read" and "Observe" capabilities.
  • Stateless Marker: As an abstract marker, it adds no runtime object overhead, serving purely as a type-system hint for the validation engine.

Usage Example:

// Create a standard mutable state atom
final settings = ValueCell<String>(value: "Active");

// Project a restricted view
final publicView = settings.unmodifiable; // Implements Unmodifiable

void inspect(Cell<String> cell) {
  if (cell is Unmodifiable) {
    print("ReadOnly: ${cell.value}");
    // cell.dispatch(Pulse("New")); // The logic gate will block this.
  }
}
