Modifiable

Modifiable class

A specialized architectural marker and base interface for objects that support controlled mutation through the framework's dynamic command pattern.

Modifiable serves as a foundational component of the cell's security and reactive architecture. In a system where data flow is primarily unidirectional and reactive, Modifiable defines the formal contract for "Mutation Entry Points"—specific methods or operations permitted to alter the state, configuration, or structural topology of a Cell.

Core Philosophy: Controlled Mutation

The framework discourages direct, unvalidated field manipulation to maintain graph integrity. Instead, any object implementing or inheriting from Modifiable is expected to adhere to the following triad:

  1. Whitelisted Operations: The object must explicitly identify which functions are capable of modifying its internal state. This is typically exposed via the modifiable getter in subclasses.
  2. Enforced Validation: Every mutation request is subjected to gatekeeping logic. By integrating with a TestCell, the object ensures that the caller possesses the appropriate authority to perform the requested change.
  3. Synchronized Access: All state transitions must occur within an atomic synchronization domain (usually governed by a Lock). This ensures that the reactive graph remains consistent and free from "torn states" during concurrent updates.

Architectural Role:

  • Command Pattern Support: Works in tandem with the Cell.apply method to facilitate a decoupled, reflection-like execution gateway. This allows components to trigger actions on a node without having compile-time knowledge of its concrete type.
  • Type Safety & Intent: Provides a clear type-safe boundary to distinguish between read-only views (Unmodifiable projections) and active, mutable components of the reactive ecosystem.
  • Proxying & Deputization: Acts as the functional base for Cell.deputy and other proxy objects. It provides the infrastructure needed for a deputy to intercept calls, perform additional security checks, and then safely delegate to the principal object.

Implementation Strategy:

While Modifiable is often used as a marker, its primary power is realized in subclasses (like CellBase or TissueBase) that implement the apply logic.

  • Mutable Instances: Return a populated whitelist of member functions.
  • Unmodifiable Instances: Typically return an empty whitelist, effectively shuttering the mutation gateway while allowing the object to remain a first-class member of the reactive graph.
