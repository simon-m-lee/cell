Synthesizes a managed Pulse instance with an exhaustive set of configuration options for complex system integration and Policy-Based Governance.

When to use

Only when you need explicit provenance – e.g., audit trails, security rules, or when the pulse must carry actor/reason/sensitivity metadata. For most signals, the plain Pulse constructor is sufficient.

How it works

You provide optional metadata like context (authority, actor, reason), priority (scheduling urgency), and policy (TTL/hop limits). The framework attaches all of this to the pulse for traceability.

Non‑obvious

  • The onComplete callback fires only after the pulse has been fully propagated through the graph – useful for coordinating side effects.
  • The policy can neutralise a pulse if it exceeds its TTL or hop limit, preventing infinite loops.

Example: High‑Integrity Update

final pulse = Pulse<int>.governed(
  payload: 42,
  type: 'system_command',
  context: PulseContext.instruction(
    baseContext: currentContext,
    actor: 'admin_service',
    directive: 'RESOURCE_OPTIMIZATION',
  ),
  priority: 10,
  step: 'initial_ingress',
);

Parameters:

  • policy: Lifecycle Governance. Defines termination constraints (TTL/Hops).
  • context: Authorization & Provenance. The authority and audit metadata.
  • payload: The Message Content. The primary data or instruction.
  • type: The Message Signature. A tag used for logic routing.
  • source: The Originating Node. The Cell that generated this signal.
  • step: The Audit Step. A description of the initial processing stage.
  • priority: Scheduling Priority. Used for urgent execution in high-contention cycles.
  • onComplete: Success callback triggered after graph-wide stabilization.
  • onError: Failure callback for validation errors or transformation exceptions.
  • onProgress: Telemetry callback for graph traversal milestones.

Returns:

A fully configured Pulse instance ready for governed propagation through the reactive fabric.
